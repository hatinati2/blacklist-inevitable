# Windows Agent recovery journal

## Implemented foundation

`src-tauri/src/recovery_journal.rs` defines a versioned, bounded, non-secret checkpoint format and a file store used by the privileged Windows Agent at service startup. The service now opens the pre-provisioned protected directory and loads every committed checkpoint before it exposes clean status. This is a fail-closed startup gate, not yet an OS reconciler: it does not start sing-box, create a TUN adapter, change routes or DNS, or install WFP filters.

A journal records only the resource identities and exact previous settings needed for recovery:

- Engine PID plus its Windows process-creation timestamp, so recovery can distinguish PID reuse.
- TUN adapter GUID, interface index, alias, MTU, and assigned addresses.
- Each route state applied by the session and the previous route state, if one existed. Route states now also retain the stable interface NET_LUID; interface indexes are diagnostic only because Windows can reuse them.
- DNS configuration per interface and IP family: adapter name servers, profile-specific name servers, effective resolver addresses, connection domain, search and supplemental search lists, dynamic-registration/LLMNR/query flags, and per-server DoH templates/options. IPv4 and IPv6 snapshots are separate; a journaled DNS mutation is valid only when both are present. The prior compact DHCP/static representation remains readable for older records.
- WFP provider/layer GUIDs, stable filter GUIDs when available, and BFE runtime filter IDs owned by the session. The stable filter GUID is the deletion/read-back key; the runtime ID is diagnostic only.

The schema does not contain profile credentials, share links, engine JSON, command lines, executable paths, or arbitrary filesystem paths. All collections and the serialized file size have explicit upper bounds. Unknown fields and unsupported schema versions are rejected.

`FirewallFilterRecord.filterKey` is optional only for compatibility with older version-1 records that predate stable filter-key recording. Newly created WFP filter records must always include a canonical filter GUID. Recovery must never attempt to delete a legacy filter using only its runtime ID; it must enumerate and reconcile exact provider-owned filters or leave policy cleanup unconfirmed.

## Storage and recovery semantics

The privileged service installer must create the journal directory before the service starts. The directory must be owned by the service identity and have a restrictive DACL that prevents modification by ordinary users. The module deliberately does not create the root directory or set its ACL.

For each checkpoint, the store validates the full record, creates a unique pending file with create-new semantics, writes and flushes its contents, then commits it under a unique session/revision filename. On Windows the commit uses `MoveFileExW` with `MOVEFILE_WRITE_THROUGH`. Incomplete pending files are ignored; a committed but corrupt, oversized, reparse-point, or filename-mismatched record makes recovery fail closed.

`load_unresolved` returns the newest committed revision for each session. A new revision must be greater than the prior committed revision. The service must reconcile every returned session against actual process, adapter, route, DNS, and WFP state before accepting a new Connect request.

`remove_session` is idempotent, but it must only be called after the service has independently verified engine exit, TUN teardown, route/DNS restoration, and WFP filter cleanup. A journal is not a substitute for checking the real operating-system state.

## Read-only reconciliation assessment

`src-tauri/src/recovery_assessment.rs` now compares a journal against an explicitly supplied OS observation snapshot. It is a pure planner and does not query Windows or perform cleanup. Each resource is classified as:

- `VerifiedClean`: positively absent or the exact prior route/DNS state is restored.
- `NeedsCleanup`: the exact journaled engine, tunnel, route, or WFP filter is still present.
- `NeedsRestore`: the exact session-applied route/DNS state still needs its recorded previous value restored.
- `Conflict`: the observation does not match the journal's ownership and expected state.
- `Unknown`: the OS observation is incomplete or cannot safely identify the resource.

The planner uses process creation time with PID, stable tunnel GUID, exact route and DNS values, and provider/layer/filter GUIDs for WFP. It deliberately ignores the WFP runtime filter ID when identifying an extant filter. A complete, positively verified empty provider inventory proves that all product filters are absent even for legacy records; if any filter remains but its stable key is missing, ownership cannot be matched and recovery stays blocked. Missing route/DNS observations, incomplete WFP enumeration, unexpected provider-owned filters, PID reuse, and conflicting resource state also keep recovery blocked.

The `can_remove_journal` result is true only when every recorded resource is positively clean and the complete provider-scoped WFP inventory confirms no product-owned filters remain. A future Windows reconciler must gather authoritative snapshots, perform cleanup/restoration using exact ownership checks, take a fresh snapshot, and only then act on this result. This planner does not itself authorize or execute destructive operations.

## Windows read-only resource observers

`src-tauri/src/recovery_observer.rs` now contains read-only Windows observation calls:

- The engine-process probe opens the journaled PID with only query and synchronize rights, checks its wait state, reads the kernel FILETIME creation value, and checks liveness again. A PID that no longer exists is reported absent; access denied, API failures, and inconclusive states are errors and must become `Unknown`. The creation timestamp is compared by the assessment planner, so PID reuse is a conflict rather than permission to terminate another process.
- The tunnel-interface probe reads `GetIfTable2` and matches the stable interface GUID, then reads the complete IPv4/IPv6 unicast address table with `GetUnicastIpAddressTable(AF_UNSPEC)`. Address rows are correlated by the adapter's stable NET_LUID and their interface index is checked as a live consistency value. The observer records and compares the assigned address plus on-link prefix length for every address, rejects duplicate/invalid/oversized inventories, and returns Unknown on any API or inventory error. Version-1 journals that predate address-prefix recording still deserialize, but their empty `addressDetails` cannot authorize a positive TUN identity match and therefore remain Unknown. See [GetUnicastIpAddressTable](https://learn.microsoft.com/windows/win32/api/netioapi/nf-netioapi-getunicastipaddresstable) and [MIB_UNICASTIPADDRESS_ROW](https://learn.microsoft.com/windows/win32/api/netioapi/ns-netioapi-mib_unicastipaddress_row).
- The route probe reads the full IPv4/IPv6 table with `GetIpForwardTable2(AF_UNSPEC)`, frees the IP Helper snapshot with `FreeMibTable`, and compares canonical destination prefixes, interface indexes, stable interface NET_LUIDs, next hops, and metrics. Legacy route records without a stable LUID remain `Unknown`; a reused interface index alone can never prove that the old route was restored. If a destination prefix has multiple rows, it reports `Unknown`: the current journal schema keys routes only by destination prefix and cannot safely disambiguate multiple interfaces.
- The WFP probe calls `WfpEngine::enumerate_owned_filters`. It begins an explicit read-only BFE transaction, positively verifies that the stable product provider and sublayer both exist with their persistent flags and expected ownership, creates a provider-key-scoped enumeration handle, reads every bounded page, verifies each returned provider and stable filter GUID, destroys the enumeration handle, and commits the read-only transaction. It returns `Present(empty)` only after the provider and sublayer have been verified and a complete successful enumeration is empty. A missing/non-persistent provider or sublayer, any API error, or an inventory above the 256-filter journal bound remains `Unknown`.
- The DNS probe calls `GetInterfaceDnsSettings` with version 3 (the only version documented by the current function reference with per-server DoH properties), setting only `Version` and leaving input `Flags` zero. It always frees the returned settings with `FreeInterfaceDnsSettings`. It separately reads the effective DNS server list from `GetAdaptersAddresses(AF_UNSPEC)`, correlating the adapter by stable NET_LUID and bounding/rejecting incomplete or cyclic linked lists. Adapter-configured and profile-configured server lists remain separate from effective resolver addresses; search/domain and per-server DoH properties are copied and validated without mutating the OS. The function returns only the IP family identified by the returned `DNS_SETTING_IPV6` bit, leaving the other family absent. Since the documented Get API does not let the caller request the second family (its input Flags must be zero), this observer is intentionally partial: the pure assessor reports `Unknown` for a journal requiring both IPv4 and IPv6. It does not authorize cleanup, restore, or journal removal. Version 4's encrypted-DNS adapter flags are retained in the journal schema but are not claimed by this observer until GetInterfaceDnsSettings documents and a supported Windows API path exposes that version.

- The separate `dns_wmi` diagnostic collector queries only the documented `root\\StandardCimv2` DNS Client classes through local `Get-CimInstance` calls. It captures per-family server-address rows, per-interface suffix/registration/DHCP properties, and global suffix policy as distinct evidence. It brackets the query with contemporaneous `GetIfTable2` reads and requires the journaled GUID plus the current, unique NET_LUID/index/alias mapping to remain consistent; WMI indices/aliases are never treated as durable identity. The current DNS journal schema persists GUID and index, not a historical NET_LUID, so the collector does not claim to compare against a journaled LUID. It rejects malformed, missing, duplicate, oversized, stale, or contradictory rows and compares each returned family server list with the current native effective server list. The PowerShell process has bounded output and execution time. Its output has a distinct diagnostic type and is not wired into `RecoverySnapshot`, the assessor, intent planner, or journal-removal decision. A WMI-only result therefore cannot turn partial DNS evidence into restore authority. This is corroboration only; it does not supply all adapter/profile server associations or per-server DoH properties and cannot close the dual-stack restoration gate. This implementation relies on the documented [MSFT_DNSClientServerAddress](https://learn.microsoft.com/windows/win32/fwp/wmi/dnsclientcimprov/msft-dnsclientserveraddress), [MSFT_DNSClient](https://learn.microsoft.com/windows/win32/fwp/wmi/dnsclientcimprov/msft-dnsclient), and [MSFT_DNSClientGlobalSetting](https://learn.microsoft.com/windows/win32/fwp/wmi/dnsclientcimprov/msft-dnsclientglobalsetting) class schemas; [Get-CimInstance](https://learn.microsoft.com/powershell/module/cimcmdlets/get-ciminstance) uses the local WMI COM session when no remote computer or CIM session is supplied.

These probes do not stop processes, create/delete filters, alter WFP policy, change routes or DNS, or remove journal files. They are not wired into the Agent startup gate; that gate remains fail-closed. The DNS observer described above is a partial diagnostic snapshot, not a recovery implementation: the unobserved family remains absent and the assessor must keep the whole DNS resource `Unknown`. Microsoft documents `Get-DnsClientServerAddress` with an `-AddressFamily` selector for IPv4 or IPv6 and describes it as returning DNS server IP addresses configured on an interface ([DnsClient reference](https://learn.microsoft.com/powershell/module/dnsclient/get-dnsclientserveraddress)). It is a candidate independent cross-check for family-specific server lists, but its documented output does not cover the full adapter/profile settings, suffix flags, and per-server DoH properties in this journal; it cannot by itself authorize restoration. Likewise, the documented `Tcpip`/`Tcpip6` `NameServer` registry paths describe a miniport-driver DNS-update contract and are not yet validated as a universal authoritative read path ([Microsoft driver documentation](https://learn.microsoft.com/windows-hardware/drivers/network/mb-dns-updates)). Do not infer missing stack state from either source. `DNS_INTERFACE_SETTINGS3` requires Windows 10 Build 19645 or later for DoH properties, so older systems cannot claim a complete DoH-capable snapshot from this API. A route with duplicate destination prefixes also remains unverified until the journal identity is extended to include the interface.

## Security boundary and remaining work

The journal is not an authentication or integrity mechanism. Its trust depends on the service-owned directory ACL and the service's validation of every record. The service must not open a user-writable directory as its journal root. Reparse-point entries are rejected, and files are never selected using a caller-supplied path.

The service now loads the journal at startup and fails closed when the directory is missing/unsafe, a committed record is corrupt, or any prior session remains unresolved. It deliberately does not guess that recorded resources are gone, delete journals, or mutate networking during this gate. The following are still release-blocking work:

- Independently verify the service-owned directory DACL when opening it; installation currently provisions and smoke-tests the protected ACL.
- Wire a checkpoint before each OS mutation and after each successful mutation.
- Implement startup reconciliation against actual process, TUN, route, DNS, and WFP state, then remove a journal only after each recorded resource is confirmed absent/restored.
- Implement rollback in reverse order and only remove journal files after verified cleanup.
- Exercise process/agent crash, forced termination, restart, tampered journal, ACL, and reparse-point cases on real Windows 10/11 machines.

A green installer build or unit test does not prove live network recovery or leak-free VPN operation.
